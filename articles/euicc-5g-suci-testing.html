Testing eUICC for 5G: validating SUCI subscriber privacy

5G hides the subscriber's permanent identity behind the SUCI. Here is how to build a test suite that proves an eUICC conceals it correctly, from protection schemes to the negative cases that catch real defects.

Rahmadani Tyas Ningrum Test Lead & Senior Automation SDET

Why SUCI exists

In 4G, a device could be asked to send its permanent subscriber identity, the IMSI, in clear text before any security context was set up. That single weakness is what made IMSI catchers practical. 5G closes the gap. Under 3GPP TS 33.501, the permanent identity is now called the SUPI, and it is never sent over the air in the clear. What travels instead is the SUCI, the Subscription Concealed Identifier: the subscriber-specific part of the SUPI encrypted with the home network's public key, so that only the home network's de-concealment function (SIDF) can recover it.

For anyone testing SIMs and eUICCs, this turns identity handling from a simple file read into a cryptographic feature. If the card computes the SUCI incorrectly, the subscriber either cannot register or, worse, registers while leaking the identity the feature was meant to protect.

Where the eUICC fits

The SUCI can be calculated either by the USIM application on the card or by the mobile equipment, depending on what the operator enables in the USIM service table. On an eUICC, the USIM lives inside an operator profile that is downloaded from an SM-DP+ server, so the configuration that drives SUCI calculation arrives with the profile:

  • Protection scheme list and priorities: which schemes the card may use, in order of preference.
  • Home network public keys, each with a public key identifier the network uses to pick the matching private key.
  • Routing indicator, which lets the network route the SUCI to the right authentication server.

When the card does the calculation itself, the device asks for it with the GET IDENTITY command defined in 3GPP TS 31.102, and the card returns a fully formed SUCI.

The three protection schemes you must cover

SchemeCurveWhat the test must prove
Null scheme (ID 0)NoneMSIN is returned unencrypted, and only when the null scheme is genuinely the configured choice.
Profile A (ID 1)Curve25519 (X25519)Output de-conceals to the correct MSIN with the home network private key; MAC tag verifies.
Profile B (ID 2)secp256r1Same as Profile A, plus the ephemeral public key is a correctly compressed point.

Both ECIES profiles share the same construction from TS 33.501 Annex C: an ECDH shared secret, the ANSI X9.63 KDF with SHA-256 to derive an AES-128 key, an initial counter block and an HMAC key, AES-128 in CTR mode for the ciphertext, and HMAC-SHA-256 truncated to 64 bits for the MAC tag.

Test your oracle before you test the card

The card generates a fresh ephemeral key pair for every SUCI, so you cannot compare its output with a fixed expected value. Instead, the test harness has to de-conceal what the card returns, playing the role of the network. That makes the harness's decoder the oracle for the whole suite, and an untested oracle is a liability.

The fix is simple: validate the decoder first against the published test vectors in TS 33.501 Annex C.4. Only once it reproduces those exactly do you point it at real cards. A minimal Profile A decoder in Python looks like this: 

from cryptography.hazmat.primitives import hashes, hmac
        from cryptography.hazmat.primitives.asymmetric.x25519 import X25519PrivateKey, X25519PublicKey
        from cryptography.hazmat.primitives.ciphers import Cipher, algorithms, modes
        from cryptography.hazmat.primitives.kdf.x963kdf import X963KDF


        def deconceal_profile_a(hn_private: X25519PrivateKey, eph_pub: bytes,
                                cipher_text: bytes, mac_tag: bytes) -> bytes:
            shared = hn_private.exchange(X25519PublicKey.from_public_bytes(eph_pub))
            keys = X963KDF(algorithm=hashes.SHA256(), length=64, sharedinfo=eph_pub).derive(shared)
            enc_key, icb, mac_key = keys[:16], keys[16:32], keys[32:]

            tag = hmac.HMAC(mac_key, hashes.SHA256())
            tag.update(cipher_text)
            if tag.finalize()[:8] != mac_tag:
                raise AssertionError("SUCI MAC tag mismatch")

            decryptor = Cipher(algorithms.AES(enc_key), modes.CTR(icb)).decryptor()
            return decryptor.update(cipher_text) + decryptor.finalize()  # BCD-encoded MSIN

A layered test model

1. Configuration

Before any cryptography, confirm the profile carries what the operator ordered: the SUCI-related files exist, their access conditions are right, and their contents match the personalisation data, including key identifiers, scheme priorities and the routing indicator.

2. Correctness

For each configured scheme, request a SUCI, de-conceal it and compare the recovered MSIN with the expected subscriber. Check the surrounding fields too: SUPI type, MCC and MNC encoding, routing indicator, scheme ID and home network public key identifier.

3. Security properties

  • Freshness: two consecutive requests must produce different ephemeral keys and ciphertexts.
  • Integrity: flip one bit of the ciphertext in the harness and confirm the MAC check rejects it, which proves the check itself works.
  • No silent downgrade: the card must not fall back to the null scheme when a protection scheme is configured.

4. Negative and lifecycle cases

This is where most real defects hide. Cover unsupported scheme identifiers, a missing or malformed public key, a key identifier that does not match, and service flags switched off. On an eUICC, also test profile lifecycle: enable a second profile and confirm that the SUCI now reflects that profile's configuration, then switch back.

Automating it

The suite I worked on was written in Python: APDUs sent to the card through a PC/SC reader, TLV parsing for the responses, and de-concealment with the cryptography library. A few practices made the biggest difference:

  • Parametrise by scheme and profile so one test body covers every combination, and new combinations cost a line of data rather than a new test.
  • Keep test keys out of the code and clearly separated from anything resembling production key material.
  • Log every APDU exchange and attach it to failures. A defect report that includes the exact command and response gets fixed far faster.
  • Run in CI against a reader farm, so regressions are caught on the build that introduced them.
In practice: structuring the suite this way, scheme by scheme and layer by layer, raised test coverage and efficiency on our eUICC 5G SUCI work by 25%, mostly by making the negative and lifecycle cases cheap enough to automate.

Key takeaways

  • SUCI turns identity handling into a cryptographic feature, so test it like one.
  • Validate your de-concealment oracle against the 3GPP test vectors before trusting any card result.
  • Test properties (freshness, integrity, no downgrade), not just outputs.
  • On eUICC, profile switching is part of the feature, not an edge case.
