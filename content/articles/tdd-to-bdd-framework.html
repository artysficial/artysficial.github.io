Where we started

Our first automation framework followed a classic test-driven style: Python test functions, fixtures for set-up, and assertions written by engineers for engineers. It worked. Tests were fast, and coverage grew. But two problems kept coming back.

  • Clients could not review our tests. When a business stakeholder asked "do you test the case where a transfer exceeds the daily limit?", the honest answer involved opening a Python file.
  • Knowledge sat in code. New QA engineers had to read implementation details to understand what a test was even checking.

Behaviour-Driven Development (BDD) addresses both by putting a readable specification on top of the automation. We moved the framework from TDD to BDD step by step, without rewriting what already worked.

Keep the engine, change the interface

The key decision was to keep the existing driver and helper layers (API clients, device drivers, data builders) and add Gherkin scenarios as a new layer above them. Step definitions became thin adapters that call into the code we already trusted. 

features/            # Gherkin: readable by clients and new joiners
  transfer.feature
steps/               # thin step definitions, no business logic
  transfer_steps.py
lib/                 # unchanged: API clients, drivers, data builders
conftest.py

A scenario reads like an acceptance criterion:

Feature: Wallet-to-wallet transfer

  Scenario Outline: Transfers respect the tier limit
    Given a verified wallet at tier "<tier>" with a balance of 500.00
    When the holder transfers <amount> to another wallet
    Then the transfer is "<result>"

    Examples:
      | tier  | amount | result   |
      | basic | 100.00 | accepted |
      | basic | 250.01 | rejected |
      | full  | 250.01 | accepted |

And the step definitions, here with pytest-bdd, stay short:

from pytest_bdd import given, parsers, scenarios, then, when

scenarios("../features/transfer.feature")


@given(parsers.parse('a verified wallet at tier "{tier}" with a balance of {balance:f}'),
       target_fixture="wallet")
def wallet(api, tier, balance):
    return api.create_wallet(tier=tier, balance=balance)


@when(parsers.parse("the holder transfers {amount:f} to another wallet"), target_fixture="response")
def transfer(api, wallet, amount):
    return api.transfer(source=wallet, target=api.create_wallet(), amount=amount)


@then(parsers.parse('the transfer is "{result}"'))
def check_result(response, result):
    assert response.status == result

Rules that kept the scenarios useful

  • Declarative, not imperative. "When the holder transfers 100.00" rather than "When I tap Send, type 100, tap Confirm". UI details belong in the step code, so scenarios survive a redesign.
  • One behaviour per scenario. If a scenario needs "and then" five times, it is testing several things.
  • A shared step vocabulary. We reviewed new steps before adding them, which prevented dozens of slightly different "Given a wallet" phrasings.
  • Tags for selection. @smoke, @regression and feature tags drive which scenarios run in which pipeline.
  • Not everything becomes BDD. Low-level technical checks (byte formats, cryptographic vectors) stayed as plain tests. BDD earns its place where behaviour matters to a stakeholder.

Migrating without stopping delivery

  1. Pick one feature with active client interest and convert its tests first.
  2. Review the feature file with the client or product owner and adjust the wording to their language.
  3. Convert further features as they are touched, rather than in one big rewrite.
  4. Retire old tests only when the new scenarios cover the same behaviour and have run green in CI.

What changed

Feature files became the document we walked through with clients when agreeing what "done" meant. Reuse across regression suites improved, because steps were shared instead of copied. And onboarding got faster: new QA engineers could read the feature files on day one, then learn the step and library layers as they went. That made the framework a teaching tool as much as a testing tool.

If you take one thing away: BDD is a communication practice that happens to run as tests. Write the scenarios for the people who need to read them, and let the code underneath do the heavy lifting.
