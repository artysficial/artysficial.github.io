The problem

Automated Android tests ran in Jenkins and produced JSON results. The client, and our own release process, needed those results in Jira test execution tickets, where each test is linked to the requirement it covers. In between sat a person copying pass and fail statuses by hand after every run.

Manual transfer was slow, but the bigger cost was trust: a status typed into the wrong row, or a run that never got reported, breaks traceability exactly when someone needs it. Working with the DevOps team, we automated the import. It cut manual reporting effort by 40% and made every execution traceable back to a build.

The pattern

  1. Tag each automated test with its Jira test key, so the mapping lives next to the code.
  2. Produce a machine-readable result file at the end of every run.
  3. Transform it into the import format of your test management add-on (Xray, for example, accepts its own JSON, JUnit XML and Cucumber JSON).
  4. Post it from the pipeline to create or update the test execution, with a link back to the build.

In the pipeline

pipeline {
  agent { label 'android' }
  stages {
    stage('Test') {
      steps { sh './gradlew connectedAndroidTest' }
    }
  }
  post {
    always {
      withCredentials([usernamePassword(credentialsId: 'xray-api',
                       usernameVariable: 'XRAY_ID', passwordVariable: 'XRAY_SECRET')]) {
        sh 'python tools/push_results.py results/report.json --build-url "$BUILD_URL"'
      }
    }
  }
}

Running the upload in post { always { ... } } matters: failed runs are the ones you most need in Jira.

The import script

A simplified version for Xray Cloud. The script authenticates, maps results to test keys and imports a test execution: 

import json, os, sys
import requests

XRAY = "https://xray.cloud.getxray.app/api/v2"


def token():
    response = requests.post(f"{XRAY}/authenticate", timeout=30, json={
        "client_id": os.environ["XRAY_ID"], "client_secret": os.environ["XRAY_SECRET"]})
    response.raise_for_status()
    return response.json()


def to_xray(results, build_url):
    return {
        "info": {"summary": "Android regression", "description": f"Jenkins build: {build_url}"},
        "tests": [{"testKey": r["jira_key"],
                   "status": "PASSED" if r["passed"] else "FAILED",
                   "comment": r.get("message", "")} for r in results],
    }


results = json.load(open(sys.argv[1]))
unmapped = [r["name"] for r in results if not r.get("jira_key")]
if unmapped:
    sys.exit(f"Tests without a Jira key: {unmapped}")

response = requests.post(f"{XRAY}/import/execution", timeout=60,
                         headers={"Authorization": f"Bearer {token()}"},
                         json=to_xray(results, sys.argv[3]))
response.raise_for_status()
print("Imported:", response.json()["key"])

Design decisions that paid off

  • Fail loudly on unmapped tests. A test without a Jira key is a traceability gap; the script refuses to hide it.
  • Link the build. Every execution carries the Jenkins build URL, so anyone in Jira can reach logs and artefacts in one click.
  • Do not let Jira break the build. If the API is down, retry, then mark the build unstable rather than failed: the tests themselves still ran.
  • Keep secrets in Jenkins credentials, never in the repository or the job configuration.
  • Make it re-runnable. Re-importing the same results should update, not duplicate, the execution.

Why it matters beyond saved hours

With results flowing automatically, the Jira dashboards reflect reality on every build. Release-readiness discussions move from "is this up to date?" to "what does it tell us?", and the requirement-to-evidence chain that regulated clients ask for is there by default rather than assembled the night before an audit.
